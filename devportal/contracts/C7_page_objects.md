# C7: page-object API and BDD vocabulary

Contract C7 of `docs/dev-portal/PLAN.md` §4.3: the method signatures of every class in `e2e-tests/pages/developers/`, and the shared BDD sentences the portal adds. A change to anything here goes through the Integrator (§4.3), who announces it in every affected inbox.

The signatures are final. A body that reads `return notImplemented('<Class>.<method>')` throws `Error('not implemented: <Class>.<method>')` until its feature lands; the workstream that builds the feature (W14 for most suites, W12 for the gallery) writes the body and must not change the signature. Methods marked **Implemented** below already work, because they do not depend on the portal's DOM.

## Rules the classes follow

- Every class extends `HelperBase` (`e2e-tests/pages/helperBase.ts`) with `constructor(page: Page, language: string)`, and is reached through `PageManager`, never constructed in a spec.
- Locators stay private inside the class; public methods are async and return data or `void`. Assertions live in specs, so methods return what a spec needs to assert on (`string`, `boolean`, arrays, small records) rather than asserting themselves.
- Every timeout goes through `t()`. Locators prefer role, then label, then text, then test id, then CSS. Accessible names come from contract C6.
- Navigation inside a test uses absolute URLs from `developersUrl(path)`, because the tag-scoped `*-sanity` and `chrome-pr` projects run the portal's tagged tests under the Library baseURL. The first navigation of a test still goes through `goToPageWithLang` / `goToPageWithUser`.
- Methods that would write (feedback, editor saves, Formstack) are paired with an interceptor that answers locally; BDD steps and `@pr` tests always install it first.
