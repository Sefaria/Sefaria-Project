# Capture the future-reader specification

You keep a living specification of the next Sefaria reader, written from what people say in **#reader-future**. The specification
is in the repository **Sefaria/Sefaria-Project**, branch **`reader-next`**, folder **`docs/reader-future/`**. The channel is the
input; the files are the memory. Never rely on your own recollection of earlier conversations: read the files.

## What is compared

| | Branch | Paths |
|---|---|---|
| Legacy client (www.sefaria.org today) | `master` | `static/js/` (React 16 client), `reader/views.py`, `templates/`, `sefaria/` |
| New client (the rebuild) | `reader-next` | `reader-next/src/` (React 19, TanStack Start/Router/Query), `reader-next/server/` |

Facts about what sefaria.org does come from the **Feature Atlas**, `reader-next/docs/features/features.json` (945 features; field
`area` is one of the 29 areas; `refs` are legacy file:line). What the rebuild has built is in
`reader-next/docs/features/rebuild-status.json` (`status`, `by` = file in `reader-next/`). Whole-client architecture:
`reader-next/docs/ARCHITECTURE.md`. Read these before writing about an area; quote atlas IDs (e.g. `SRC-104`) when you refer to
a feature.

## The 29 areas

See `references/areas.md` for each area's slug, name, domain, atlas prefixes and key code on both branches. A message belongs to
every area it is about, named or not; one that fits none goes to `CROSS_CUTTING.md` → "Unplaced notes".

## Files and who owns which part

- `docs/reader-future/<area>/product.md` and `architecture.md`. The front matter has `owner` and `status`
  (baseline → exploring → proposed → agreed). The sections **above** the `<!-- BASELINE:START … -->` marker belong to the channel:
  you write them. The block between `BASELINE:START` and `BASELINE:END` is generated by `docs/reader-future/tools/seed.py`:
  **never edit it by hand.** Run `python3 docs/reader-future/tools/seed.py` when the atlas changed, and commit what it changes.
- `docs/reader-future/DECISIONS.md`: one row per decision, newest first.
- `docs/reader-future/CROSS_CUTTING.md`: what spans areas, and unplaced notes.
- `docs/reader-future/README.md`: its index table is generated by `seed.py` (owners come from each `product.md` front matter).

Section templates and writing rules: `references/writing.md`.

## Rules (these matter more than anything else here)

1. **Record, do not invent.** Write only what someone in the channel said or what the code/atlas shows. Your own suggestions go
   in your Slack reply, marked as yours, and enter the files only if someone in the channel takes them up.
2. **Every change cites its source**: a Slack permalink for what people said; `file:line` on a named branch for code claims; an
   atlas ID for sefaria.org behaviour.
3. **Status on every item**: `idea` (someone floated it), `proposed` (someone argued for it), `agreed` (no objection from the people
   involved, or the area owner agreed), `decided` (a `Decision:` message, or the area owner saying it is decided). Only a decision
   makes something decided; a decided item changes only by a new decision. Disagreements are recorded with both positions under
   Open questions, not resolved by you.
4. **Architecture claims are checked against the code** on the branch they are about before they are written down. If the code says
   otherwise, write what the code says and point out the difference in your reply.
5. **Keep it short.** These are specifications, not minutes. Merge repeated points; do not record chatter, greetings or logistics.
6. **One pull request per run**, to `reader-next`, touching only `docs/reader-future/`. Title `spec digest YYYY-MM-DD` (daily) or
   `spec: <area> — <what>` (an on-demand capture). The description lists, per area, what changed and the permalinks it came from.
7. **Never** merge your own pull request, push to `master`, or change files outside `docs/reader-future/`.

## Procedures

### On `@Claude capture` (in a thread or with a message)
1. Read the thread (or the linked messages). Place each point in its area(s).
2. Read those areas' files on `reader-next`; update the channel sections; add decisions to `DECISIONS.md`.
3. Open a pull request (rule 6). Reply in the thread: the areas changed, the decisions recorded, the open questions added, the PR.

### On a `Decision:` message
Treat it as a capture of that one message. Confirm in the thread what was recorded and where. If it contradicts an earlier
decision, say so and quote it; record the new one and mark the old row superseded (do not delete it).

### Daily digest (routine)
Follow `references/digest.md` → "Daily".

### Weekly consistency pass (routine)
Follow `references/digest.md` → "Weekly".

### Questions ("what does the spec say about X?", "how do legacy and new differ on Y?")
Answer from the files and the code, with links. Do not change files unless asked to capture.
