# End-to-end tests

The specs in this folder run the real app (the dev server, and the production build for `ssr-styles.spec.ts`) against the API
cassette (`scripts/api-cassette.mjs`): recorded answers of www.sefaria.org, so live data changes cannot turn the suite red.

## What CI runs

The `e2e` job of `.github/workflows/reader-next-client.yaml`, on every pull request and push that touches the reader:

| Step                         | Command                             | Covers                                                 |
| ---------------------------- | ----------------------------------- | ------------------------------------------------------ |
| Desktop                      | `npx playwright test --project=desktop` | every spec, Desktop Chrome at 1280×900             |
| Phone                        | `npx playwright test --project=mobile`  | the tests tagged `@mobile`, on a Pixel 7           |
| Production build             | `npm run test:e2e:prod`             | `ssr-styles.spec.ts` against `node server/index.mjs`   |

All three replay the bundle pinned by `cassette.lock` (`scripts/cassette/bundle.mjs fetch --strict`): a lock whose bundle cannot be
downloaded fails the job rather than recording from the live site. In replay, a request with no recording is answered 504 and fails
the run at the end (`cassette-misses.ts`), unless it is listed in that file's `ALLOWED_MISSES` with the reason. The list holds two entries: the Hebrew translations list API,
which www.sefaria.org answers with a 500 that the cassette never records (a test checks the page without it), and the next entries
of the Klein Dictionary and Jastrow, which the column keeps loading after a ref-corpus landing as far as timing lets it.
To run locally the way CI does: `E2E_API_MODE=replay npx playwright test --project=desktop` once `e2e/.cassette` matches the lock
(`node scripts/cassette/bundle.mjs verify`).

## What CI does not run, and why

| Not run                                                                                       | Why                                                                                                                                                                                                                                                                                                                                                     | How to run it                                                                                                                                                                        |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The signed-in tests against the stand-in Django (`E2E_STANDIN=1`): `library-pages.spec.ts` "signed in (stand-in Django)" (5 tests), `routing-pass-through.spec.ts` "a signed-in reader's 404 page" (1) | The stand-in (`scripts/exits-crawl.mjs --serve`) proxies www.sefaria.org. Pointed at the cassette (`EXITS_UPSTREAM=http://localhost:<cassette port>`) in replay, the signed-in pages ask for answers the pinned recordings do not hold (`GET /api/library-assistant`, a `GET /api/v3/texts/Sefer HaChinukh 1:1…` with the signed-in reader's versions), and one test then times out. Running it against the live site in CI would make the suite depend on today's data. Adding it needs new recordings and a new bundle. | Start the stand-in (the command at the top of each spec), then `E2E_PASS_THROUGH_URL=http://localhost:<its port> E2E_STANDIN=1 npx playwright test e2e/library-pages.spec.ts e2e/routing-pass-through.spec.ts` |
| `auth-signed-in.spec.ts` (4 tests)                                                            | Needs a deployed site (`READER_E2E_BASE_URL`) and real test accounts; CI has neither.                                                                                                                                                                                                                                                                   | Against an opt-in deployment, with the accounts named in the spec's header.                                                                                                          |
| `exits.spec.ts` (1 test)                                                                      | Crawls the live site for about 45 minutes. Its own workflow, `reader-next-exits.yaml`, runs the crawl weekly and on demand (report only).                                                                                                                                                                                                              | `EXITS_CRAWL=1`, or "Run workflow" on that workflow.                                                                                                                                 |
| `follow-ws.spec.ts` (1 test)                                                                  | Needs the follow-me room server (`npm run room:dev`).                                                                                                                                                                                                                                                                                                   | `npm run room:dev`, a reader started with `PUBLIC_ROOM_URL` pointing at it, then the spec with `FOLLOW_WS_BASE` set to that reader (it is skipped without it; the spec's header has the commands).                                                                                                                                            |
| The rest of the suite against the production build                                            | Only `ssr-styles.spec.ts` runs against the build; everything else runs against the dev server. `smoothness.spec.ts` in particular subtracts the scroll engine's own corrections, which only a dev build reports.                                                                                                                                       | `npm run build`, then `npx playwright test -c playwright.prod.config.ts` with that config's `testMatch` widened.                                                                    |
