# Hidden-book link query experiment — 14 October 2026

PR #3784 has a reproducible query failure on the development MongoDB server: hiding just **Chafetz Chaim on Sifra** expands to 1,468 title strings and makes an unrelated `Genesis 1:1` link query fail. MongoDB reports `Regular expression is invalid: regular expression is too large` (code 51091). The BSON query is 91,326 bytes. This is a regex compilation failure, not the BSON document-size limit.

## Bounded ORM results

Medians of six measured repetitions, excluding one warm-up. Actual LinkSet hydration of up to 10,000 links, using `{}` as the source query. Each baseline is paired within the PR process with filtering disabled; filtered runs use the actual PR visibility mechanism.

The separate master cauldron took 67.63 ms for the same bounded hydration. With ten flagged indexes, paired bounded hydration increased about 35%. The Genesis book and exact-passage queries also failed in every filtered trial at 100 and 1,000 flags. For ten flags their median hydration times were 542.63 → 567.69 ms and 15.76 → 19.69 ms respectively.

## Failure reproduction

1. In the experimental database only, restore the fixture to zero flags.
2. Set `admin_only: true` on the Index whose title is `Chafetz Chaim on Sifra`.
3. Refresh `admin_only_titles(force_refresh=True)` in a process with filtering enabled.
4. Query the actual LinkSet filter for `{"refs":"Genesis 1:1"}`, even with limit 1.
5. Observe Mongo error 51091; restore the original flag afterward.

In the deterministic nested fixture, 42 indexes passed and 43 failed because the 43rd selected index was this complex book. This is not a universal 43-book threshold: schema title expansion and regex complexity matter more than book count. The isolated single-book reproduction is recorded in `single-complex-book.log`; the search is in `threshold-probe.log`.

## Controls and limits

- Two standard cauldrons, separate databases, same snapshot `private_dump_small_14.10.26.tar.gz`, chart 0.90.4, matching app resource limits (1 CPU, 3 GiB RAM), no KEDA scale-to-zero. MongoDB version 4.4.30.
- Both restored 6,603 Index records, 11,914 version records and 5,064,617 links. Collection index definitions and the BSON hashes of the first 100 records in each collection matched before testing. This is sampled content verification, not a full-database checksum.
- Both databases share the development Mongo server. Runs were sequential, with deterministic shuffled baseline/filtered order inside the PR process. Shared-server load and cache effects remain possible; these are not production latency predictions or reliable p95 estimates.
- Control deployed source: `477c5e12f1`. Experimental deployed source: `37d88bdc462409ce541256ad3e76ff8e361b8676`, incorporating PR #3784 head `9c83086d0456f3b06cd6573b1f50a3d3468b8711` and master `3910579367`. Control differs from that master in deployment metadata only. Images were pinned.
- The same local benchmark script was streamed into both deployed images; exact script hashes are recorded in `experiment.json`. Query execution uses the real deployed model code.
- Fixture selection is stable SHA-256 title order, nested across counts. Only experimental Index flags were changed, with original values saved in a separate ledger. Link and version contents were untouched.
- Django/library bootstrap uses visibility enabled for consistent initialization; measured queries explicitly toggle visibility. Title-cache refresh and query-building timings are recorded separately and excluded from the reported execution/hydration times. This does not test public startup, HTTP requests, authorization or application-wide correctness.
- All test flags were restored to their original values after measurement. Both cauldrons remain available for follow-up comparisons.
